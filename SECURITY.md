# Security and privacy

## Reporting a vulnerability

Do not open a public issue for a vulnerability that could expose credentials, private message metadata, or cross-lineage data. Use GitHub's private vulnerability reporting for this repository. Include the affected version, reproduction conditions, and the smallest safe proof of impact.

## Data-minimization contract

Agent Beacon events may contain only typed, allow-listed status data required to explain a verified state transition. They must not contain:

- prompts, goals, hidden reasoning, or chain of thought
- raw tool arguments, results, logs, or stack traces
- API keys, tokens, passwords, cookies, connection strings, or credential material
- provider-internal identifiers or billing data
- message bodies unrelated to the rendered status claim

Account identity must be a stable, non-secret fingerprint generated by the host integration. A raw token or profile name is not an acceptable substitute.

## Isolation contract

Every registry, persistence, and rendering decision is scoped by the full tuple:

```text
(profile, platform, account, chat_id, topic_id, session_key, run_id)
```

Evidence is isolated by the complete lineage key. Host adapters must reject any
evidence that does not match the lineage they are currently evaluating. Closed
`run_id` values are never reopened.

## Fail-closed adapter behavior

When an adapter cannot prove current-run worker activity, cannot resolve exact routing, sees an unsupported Hermes shape, or raises during a live decision, it must emit no Beacon message. It must never fall back to a generic “still working” or “waiting for a subagent” claim.

`off` and `shadow` preserve host-visible output. `live` requires explicit host-version integration tests and an immediate rollback path.

## Supported versions

Security fixes target the latest released minor version. Pre-release and unreleased host integrations are best-effort until their contract tests are part of a tagged release.
